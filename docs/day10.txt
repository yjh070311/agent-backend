📅 Week 2 / Day 3（Day 10）：数据库接入（SQLAlchemy + SQLite）

📌 今日核心死磕

1. [[PostgreSQL 数据建模]] + ORM — 从 JSON 文件到关系型数据库

它是什么： ORM（对象关系映射）让你用 Python 类操作数据库表——User 类对应 users 表，user.name = "张三" 对应 UPDATE users SET name=...。SQLAlchemy 是 Python 最主流的 ORM。表之间的关系（一对多、多对多）用外键表达：一个 User 有多个 Conversation，一个 Conversation 有多条 Message。

它解决 Agent 工程里的什么痛点： Week 1 用 JSON 存对话历史——单机、单文件、查询要全读进内存、并发写会冲突。Agent 项目要存用户、会话、消息、面试记录，还要按用户查、按时间排序、分页——这些是数据库的看家本领。JSON 文件在数据量变大、多人同时访问时立刻崩溃。

今天为什么必须学： 今天把 Week 1 的 JSON 历史替换成 SQLite 数据库，定义 User、Conversation、Message 三张表。这个「用户→会话→消息」的三层结构是 Week 3-8 AI-Interview 的持久化地基——面试记录、简历、评分报告都挂在类似的结构上。

新手最容易踩什么坑：
- 混淆「模型类」和「表」——class User 是模型，users 是表名，一个模型实例是表里的一行
- 不理解 Session（会话）——它不是 HTTP session，是「数据库操作的工作区」，忘 commit 数据就没了
- 外键关系只定义了一边（Conversation.user_id 有，但 User.conversations 没写 relationship），反向查询就做不了

---

2. [[Python 项目分层]] 的数据库落地 — database.py 的职责

它是什么： 数据库相关的三件事要分离：引擎（engine，管理连接）、会话工厂（SessionLocal，每次请求一个独立会话）、模型基类（Base，所有 ORM 模型继承它）。这三者集中在 database.py 一个文件。

它解决 Agent 工程里的什么痛点： 如果每个路由都自己 create_engine() 建连接，会有一堆连接泄漏和配置重复。集中管理后，连接池配置只写一次，路由通过依赖注入拿 Session，用完自动关闭——这是 FastAPI 的标准数据库模式。

今天为什么必须学： 今天要写 database.py，这是 Week 2 后续所有数据库操作的基础。写错了（比如 Session 不关闭），Week 4-7 数据量上来后就会连接泄漏、服务假死。

新手最容易踩什么坑：
- 全局共用一个 Session，并发请求互相污染——必须「每次请求一个新 Session」
- 忘了 session.close()，连接池耗尽——正确做法是用 Depends 依赖注入 + finally 关闭
- SQLite 和 PostgreSQL 的差异不重视——SQLite 是单文件，PostgreSQL 是服务器；今天用 SQLite 本地开发，Week 5 会切 PostgreSQL

app/database.py

"""
数据库基础设施——SQLAlchemy 的引擎、会话工厂、模型基类。

三件套的作用：
    engine       —— 管理数据库连接池，全局只建一个
    SessionLocal —— 会话工厂，每次请求生成一个独立 Session
    Base         —— 所有 ORM 模型的基类，模型继承它来注册

为什么每次请求要新 Session：
    Session 是「数据库操作的工作区」，有自己的缓存和事务状态。
    如果全局共用一个，两个并发请求会互相污染对方的未提交数据。

get_db 依赖注入模式：
    FastAPI 用 Depends(get_db) 给路由注入 Session，
    请求结束时自动关闭——这是官方推荐的标准模式。
"""

from pathlib import Path

from sqlalchemy import create_engine
from sqlalchemy.orm import DeclarativeBase, sessionmaker, Session

# 数据库文件路径——放在项目根目录的 data/ 下
# SQLite 是单文件数据库，不需要单独跑服务，适
PROJECT_ROOT = Path(__file__).resolve().parent.parent
DATA_DIR = PROJECT_ROOT / "data"
DATA_DIR.mkdir(exist_ok=True)  # 确保 data/ 目录存在

DATABASE_URL = f"sqlite:///{DATA_DIR / 'agent_backend.db'}"

# connect_args={"check_same_thread": False} 是 SQLite + FastAPI 的必要配置：
# FastAPI 可能在不同线程处理请求，SQLite 默认禁止跨线程用同一连接
engine = create_engine(
    DATABASE_URL,
    connect_args={"check_same_thread": False},
    echo=False,  # 改成 True 可以看到每条实际执行的 SQL，调试时有用
)

# 会话工厂——不直接建 Session，而是每次调用 SessionLocal() 生成新的
SessionLocal = sessionmaker(bind=engine, autoflush=False, autocommit=False)


class Base(DeclarativeBase):
    """所有 ORM 模型的基类。

    模型继承 Base 后，会被自动注册到 Base.metadata，
    这样 create_all() 时能一次性建出所有表。
    """
    pass


def get_db():
    """FastAPI 依赖注入——给路由提供一个自动关闭的 Session。

    用法（在路由函数参数里）：
        @router.get("/xxx")
        async def xxx(db: Session = Depends(get_db)):
            ...

    这个 generator 在请求结束后会自动执行 finally 里的 close()，
    保证连接不会泄漏——这是数据库模式里最容易出错、也最关键的一点。
    """
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()  # 无论请求成功还是异常，都关闭 Session

app/models/user.py

"""用户模型——对应 users 表。"""

from datetime import datetime, timezone

from sqlalchemy.orm import Mapped, mapped_column, relationship

from app.database import Base


class User(Base):
    """用户表。

    一个用户可以有多个会话（一对多关系）。
    """

    __tablename__ = "users"

    # Mapped[int] 是 SQLAlchemy 2.0 的类型注解风格
    # primary_key=True 主键，auto 自增
    id: Mapped[int] = mapped_column(primary_key=True, autoincrement=True)

    # unique=True 用户名唯一，index=True 加速按用户名查询
    username: Mapped[str] = mapped_column(String(50), unique=True, index=True, nullable=False)

    # 密码哈希——绝不明文存密码（Week 2 Day 6 讲哈希）
    password_hash: Mapped[str] = mapped_column(String(255), nullable=False)

    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True),
    # relationship 定义反向关系——通过 user.conversations 拿到该用户的所有会话
    # cascade="all, delete-orphan"：删除用户时级联删除其所有会话
    conversations: Mapped[list["Conversation"]] = relationship(
        back_populates="user",
        cascade="all, delete-orphan",
    )

    def __repr__(self) -> str:
        """调试时打印友好的用户信息，不打印密码哈希。"""
        return f"<User id={self.id} username={self.username!r}>"

app/models/conversation.py

"""会话模型——对应 conversations 表。"""

from datetime import datetime, timezone

from sqlalchemy import String, DateTime, ForeignKey
from sqlalchemy.orm import Mapped, mapped_column, relationship

from app.database import Base


class Conversation(Base):
    """会话表——一次完整的对话。

    一个会话属于一个用户（多对一），包含多条消息（一对多）。
    """

    __tablename__ = "conversations"

    id: Mapped[int] = mapped_column(primary_key=True, autoincrement=True)

    # 外键指向 users.id，ondelete="CASCADE" 让数据库层也级联删除
    user_id: Mapped[int] = mapped_column(
        ForeignKey("users.id", ondelete="CASCADE"),
        nullable=False,
        index=True,
    )

    # 会话标题——方便列表展示（可以取第一条消息的前 N 字）
    title: Mapped[str] = mapped_column(String(100), default="新对话")

    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True),
        default=lambda: datetime.now(timezone.utc),
    )

    # 反向关系
    user: Mapped["User"] = relationship(back_populates="conversations")
    messages: Mapped[list["Message"]] = relationship(
        back_populates="conversation",
        cascade="all, delete-orphan",
        order_by="Message.created_at",  # 按时间排序，查询时自动有序
    )

    def __repr__(self) -> str:
        return f"<Conversation id={self.id} title={self.title!r}>"

app/models/message.py

"""消息模型——对应 messages 表。"""

from datetime import datetime, timezone

from sqlalchemy import String, Text, DateTime, ForeignKey
from sqlalchemy.orm import Mapped, mapped_column, relationship

from app.database import Base
class Message(Base):
    """消息表——单条对话消息。

    一条消息属于一个会话（多对一）。
    role 和 content 对应 LLM messages 的结构（复用 Week 1 的概念）。
    """

    __tablename__ = "messages"

    id: Mapped[int] = mapped_column(primary_key=True, autoincrement=True)

    conversation_id: Mapped[int] = mapped_column(
        ForeignKey("conversations.id", ondelete="CASCADE"),
        nullable=False,
        index=True,
    )

    # role 用 String 而非 Enum——保留灵活性，校验放在 Pydantic 层
    role: Mapped[str] = mapped_column(String(20), nullable=False)

    # Text 用于长内容，String 有长度限制，Text 更适合 LLM 消息
    content: Mapped[str] = mapped_column(Text, nullable=False)

    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True),
        default=lambda: datetime.now(timezone.utc),
    )

    # 反向关系
    conversation: Mapped["Conversation"] = relationship(back_populates="messages")

    def __repr__(self) -> str:
        preview = self.content[:30] + "..." if len(self.content) > 30 else self.content
        return f"<Message id={self.id} role={self.role} content={preview!r}>"

你需要观察什么

1. `db.add(user)` 通常只把对象放进 Session 的待处理区；`flush()` 才把 INSERT 发给数据库并取得自增 ID，但事务还没提交。`commit()` 提交事务后数据才持久化；如果只 flush 后关闭/回滚，数据不会保存。
2. `relationship` 让 Python 对象可以沿关系访问数据；这不等于 SQL 的 JOIN，也不等于 cascade。默认懒加载时，访问 `user.conversations`、`conversation.messages` 会按需发 SELECT，循环访问很多父对象时可能出现 N+1 查询。示例用 `selectinload` 预加载关系，通常分别查询用户、会话、消息三批数据。
3. `cascade="all, delete-orphan"` 是 ORM 对象操作的传播规则：删除 User 时 SQLAlchemy 会处理其 Conversation 和 Message；`ForeignKey(..., ondelete="CASCADE")` 是数据库级外键规则。SQLite 默认不强制外键，所以 `database.py` 还要打开 `PRAGMA foreign_keys=ON`。关系加载是“查”，级联删除是“删”，不要混为一谈。
4. `echo=True` 可以观察 ORM 实际发出的 SQL（如 `INSERT INTO users ...`），帮助理解 ORM 底层并非“魔法”。查看后应改回 `False`，避免日志输出过多。

今日重点概念

- **ORM 的底层作用**：模型类和字段先变成 SQLAlchemy 的映射元数据；Session 跟踪对象变化；SQLAlchemy 根据这些变化生成 SQL，通过 Engine/连接交给 SQLite 执行，再把查询行还原为 Python 对象。ORM 减少重复的 SQL/映射代码，但不会替你设计表、理解事务或消除性能问题。
- **Engine / SessionLocal / Session / Base**：Engine 管理数据库连接池；SessionLocal 是创建 Session 的工厂；每个请求/工作单元使用独立 Session 管理身份映射缓存和事务；Base.metadata 收集模型表结构供建表或迁移工具读取。
- **外键与关系**：`conversations.user_id → users.id`、`messages.conversation_id → conversations.id` 是数据库里的引用约束；`relationship(..., back_populates=...)` 是 ORM 侧的双向对象导航，两者配合但职责不同。
- **查询加载策略**：延迟加载方便按需取关系，但逐行访问可能造成 N+1；`selectinload` 用额外的批量 SELECT 预加载集合关系，适合一对多列表；`joinedload` 用 JOIN 装配对象，对集合关系可能放大结果行数。应结合 SQL 和实际查询量选择。
- **Session 生命周期**：创建 Session → 查询/修改对象 → `flush`（需要提前拿 ID 或检查 SQL 时）→ `commit`；失败时 `rollback`；最后总是 `close`。FastAPI 的 `get_db` 用 `yield` + `finally` 确保关闭。Session 不是 HTTP 会话，也不应被多个并发请求共用。
- **建表与迁移**：`Base.metadata.create_all()` 适合教学/新建本地库，只创建缺少的表，不会可靠地修改已有表结构；结构演进应使用 Alembic migration。
