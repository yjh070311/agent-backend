 Week 2：FastAPI 后端骨架

1. 核心技术拆解

技术点 A：[[FastAPI 项目结构]] + [[FastAPI 路由]]

学什么： FastAPI 的分层结构（main.py / routers/ / schemas/ / services/ / models/）、路由装饰器（@app.get / @app.post）、路径参数与查询参数、async def 路由。

为什么对 Agent 开发重要： Week 3-8 的 AI-Interview 主项目就是一个 FastAPI 服务。简历解析、岗位匹配、RAG 出题、AI 评分——每个模块都是一个路由或一组路由。Week 1 的 LLMClient 是「可被调用的库」，Week 2 要把它变成「可被 HTTP 调用的服务」。

本周用在哪里： 搭建 agent-backend 项目骨架，把 Week 1 的 LLM 调用能力包成 HTTP API。

常见错误认知：
- 把 FastAPI 当 Flask 写——所有逻辑塞在路由函数里，路由函数 200 行
- async def 路由里调用同步阻塞函数（httpx.Client），把事件循环卡死
- 不用 Pydantic 校验，手动 request.json() 然后一堆 if 判断字段存在性

关联笔记：[[FastAPI 项目结构]]、[[FastAPI 路由]]、[[Pydantic 数据校验]]、[[Python 异步编程]]

---

技术点 B：[[Pydantic 数据校验]]

学什么： BaseModel、字段类型注解、Field 校验（min_length、ge、正则）、嵌套模型、model_dump()。

为什么对 Agent 开发重要： Agent 的输入输出都是结构化数据——简历解析要输出候选人画像（dict），岗位匹配要输出匹配结果（dict）。Pydantic 把这些「自由格式的 dict」变成「有类型、有校验、有默认值的模型」。它还是 Function Calling 的 JSON Schema 自动生成基础。

本周用在哪里： 定义请求/响应模型（ChatRequest、ChatResponse），校验客户端传来的数据。

常见错误认知：
- 把 Pydantic 模型当普通 dict 用，不理解 model_validate / model_dump 的转换
- 校验规则全靠 if 手写，不用 Field 声明式校验
- 响应模型里泄露敏感字段（如密码 hash）

关联笔记：[[Pydantic 数据校验]]、[[JSON API]]、[[异常处理]]

---

技术点 C：SQLAlchemy / Tortoise ORM + [[PostgreSQL 数据建模]]

学什么： ORM 对象关系映射、模型定义（表结构）、Session 管理、增删改查。

为什么对 Agent 开发重要： Week 1 用 JSON 存历史，但 Agent 项目要存用户、会话、消息、面试记录——这些需要关系型数据库。ORM 让你用 Python 类操作数据库，不用手写 SQL。

本周用在哪里： 把对话历史从 JSON 迁移到 SQLite（本地开发），定义 User、Conversation、Message 三个表。

常见错误认知：
- 以为 ORM 能完全替代 SQL 理解——性能问题、复杂查询还是得懂 SQL
- 不管理 Session 生命周期，连接泄漏
- 同步 ORM 在 async def 路由里阻塞

关联笔记：[[PostgreSQL 数据建模]]、[[Python 项目分层]]

4. 面试仿真模拟

Q1：FastAPI 和 Flask 有什么区别，为什么选 FastAPI？

▎ 原生 async 支持（Flask 3 才有）、自动 API 文档（/docs）、Pydantic 集成校验、依赖注入系统。Agent 后端要大量并发调用 LLM，异步是刚需。

Q2：你的 async def 路由里能直接调用同步的数据库操作吗？

▎ 不能直接调同步阻塞 ORM，会卡死事件循环。要用 async 的 ORM（Tortoise）或把同步操作丢到线程池（run_in_threadpool），否则一个慢查询拖垮整个服务。

Q3：JWT 为什么是「无状态」认证？和 session 比优劣？

▎ JWT 把用户信息编码在 token 里，服务端不存状态，天然适合水平扩展。缺点是无法主动失效（除非加黑名单），泄露后有效期内容易被滥用。

Q4：你怎么处理「业务错误」和「HTTP 错误」的关系？

▎ 用自定义业务异常 + 全局 exception_handler，把业务语义（如「余额不足」）映射成规范的 HTTP 状态码和 JSON 结构，而不是到处 raise HTTPException。

📅 Week 2 / Day 1（Day 8）：FastAPI 项目结构与首个路由

📌 今日核心死磕

1. [[FastAPI 项目结构]] — 从「脚本」到「服务」的第一跳

它是什么： FastAPI 项目不是单文件，而是一棵分层目录树：main.py（入口）、routers/（路由层）、schemas/（数据模型）、services/（业务逻辑）、models/（数据库模型）、utils/（工具）。

它解决 Agent 工程里的什么痛点： Week 1 的 main.py 是「命令行入口」，用户本地敲键盘。Week 2 的 main.py 是「HTTP 服务入口」，客户端（浏览器、curl、未来的前端、未来的 Agent）通过 HTTP 调你。这个转变要求结构更严谨——因为服务会一直跑、多人调用、不能随便崩。分层结构让每个请求的处理路径清晰可追踪。

今天为什么必须学： 今天要搭 agent-backend 项目骨架。骨架搭得对不对，决定了 Week 3-8 往里面加简历解析、RAG、Agent 时是「顺畅叠加」还是「不断返工」。

新手最容易踩什么坑：
- 把 FastAPI 应用写在单个 main.py 里，路由、逻辑、模型全混——Week 3 加 RAG 时直接爆炸
- 不理解 uvicorn 和 main:app 的冒号语法——main 是文件名，app 是里面的变量名
- 启动命令用 python main.py（这是 Flask 的启动方式），FastAPI 要用 uvicorn main:app --reload

---

2. [[FastAPI 路由]] — HTTP 动词到函数的映射

它是什么： 路由装饰器（@app.get("/health")）把「HTTP 请求」映射到「Python 函数」。路径参数（/users/{id}）从 URL 提取变量，查询参数（/items?page=2）从问号后解析，请求体（POST 的 body）通过 Pydantic 模型接收。

它解决 Agent 工程里的什么痛点： Agent 后端对外暴露的能力就是一组路由——POST /chat（对话）、POST /resume/parse（简历解析）、GET /jobs/match（岗位匹配）。路由设计就是 API 设计，直接决定前端和别的 Agent 怎么用你的服务。

今天为什么必须学： 今天写 GET /health（健康检查）和 POST /chat（对话）。/health 是所有服务的标配——负载均衡器和监控系统靠它判断「服务还活着吗」；/chat 是第一个业务路由，把 Week 1 的 LLM 能力暴露成 HTTP。

新手最容易踩什么坑：
- 路由函数名写 async def chat() 但里面 time.sleep()——阻塞事件循环
- 路径参数 {id} 和查询参数 ?id=1 分不清，混用导致路由匹配失败
- 不写 response_model，返回什么全靠自觉——文档里类型显示为 unknown

app/main.py

"""
FastAPI 应用入口。

启动方式（重要，不是 python main.py）：
    uvicorn app.main:app --reload

    app.main → Python 模块路径（app/main.py）
    app     → main.py 里的 FastAPI 实例变量名

FastAPI 和 Week 1 CLI 的本质区别：
    Week 1 的 main.py 是「命令行程序」，用户敲键盘触发。
    这里的 main.py 是「HTTP 服务」，客户端通过 HTTP 请求触发。
    服务会常驻运行，持续监听 8000 端口。
"""

from fastapi import FastAPI

from app.routers import health, chat

# 创建 FastAPI 应用实例
# title 和 version 会显示在自动文档 /docs 里
app = FastAPI(
    title="Agent Backend",
    description="AI Agent 后端服务骨架（Week 2）",
    version="0.1.0",
)

# 挂载路由——把各模块的路由注册到应用上
# 每个 router 有自己的 prefix 和 tags，见各自文件
app.include_router(health.router)
app.include_router(chat.router)


# 根路径——访问 http://127.0.0.1:8000/ 时的提示
@app.get("/")
async def root() -> dict[str, str]:
    """根路由——返回欢迎信息，指向文档地址。

    注意：
        - async def：FastAPI 原生支持异步路由
        - -> dict[str, str]：返回值类型注解，会自动写入文档
    """
    return {"message": "Agent Backend 已启动，访问 /docs 查看接口文档"}

app/schemas/chat.py

"""
对话接口的请求/响应模型。

Day 1 版本先用最简单的字段，Day 2 会扩展 Field 校验和嵌套模型。
"""

from pydantic import BaseModel


class ChatRequest(BaseModel):
    """对话请求体。

    客户端 POST /chat 时，body 必须是这个结构：
    {"message": "你好"}

    如果缺少 message 字段或类型不是 str，FastAPI 自动返回 422。
    """
    message: str
class ChatResponse(BaseModel):
    """对话响应体。

    服务端返回给客户端的结构。Day 3 接入 LLM 后会加更多字段
    （如 usage、model 等）。
    """
    reply: str
    model: str = "echo"  # Day 1 先返回 echo，Day 3 换成真实模型名

app/routers/chat.py

"""
对话路由。

Day 1 版本：先返回 echo（把用户消息原样返回），验证请求/响应链路通了。
Day 3 会把 echo 换成真实的 LLM 调用（复用 Week 1 的 LLMClient）。
"""

from fastapi import APIRouter

from app.schemas.chat import ChatRequest, ChatResponse

router = APIRouter(prefix="/chat", tags=["对话"])


@router.post("", response_model=ChatResponse)
async def chat(request: ChatRequest) -> ChatResponse:
    """对话接口——接收消息，返回回复。

    Args:
        request: 校验过的请求体（Pydantic 自动解析和校验）。

    Returns:
        ChatResponse 对象（FastAPI 自动序列化成 JSON）。

    关键点：
        - response_model=ChatResponse：告诉 FastAPI 返回类型，
          文档里会显示，多余的字段也会被过滤
        - request.message：因为声明了 ChatRequest 类型，
          FastAPI 已经帮我们解析并校验了 body，这里直接用属性
    """
    # Day 1：echo 逻辑（回显用户输入）
    # Day 3：换成 client.chat(request.message)
    reply = f"你刚才说的是：{request.message}"

    return ChatResponse(reply=reply)

你需要观察什么

1. uvicorn app.main:app --reload 的冒号语法：app.main 是模块路径（app/main.py），app 是那个文件里的 FastAPI 实例名。--reload 让你改代码保存后自动重启，开发必备。
2. /docs 自动文档的威力：打开 http://127.0.0.1:8000/docs，能看到所有接口、每个接口的请求/响应结构、甚至能直接在页面上「Try it out」发请求。这是 FastAPI 秒杀 Flask 的功能之一——文档和代码同步，不会过时。
3. 422 校验错误：发一个缺 message 字段的 POST 请求，看返回的 422 错误体。里面有精确的字段定位——这是 Pydantic 自动生成的，Day 2 会深入。
4. response_model 的作用：把 ChatResponse 的 model 字段改成 model="echo"，观察文档里响应结构的变化。这个声明让返回类型有约束，多余字段会被自动过滤。
